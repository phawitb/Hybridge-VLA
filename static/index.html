1. System Overview

Hybridge VLA is a Vision-Language-Action system that converts natural language instructions into structured robotic execution plans. It uses Google Gemini VLM models to analyze images and generate step-by-step plans with bounding box coordinates for a single-arm robot with one gripper.

The system provides:

  • Plan generation from natural language instructions via Gemini VLM
  • Automatic prompt generation from a configurable template
  • Plan verification with auto-retry
  • Auto-normalization of pixel bounding boxes to [0,1]
  • Plan visualization with bounding boxes overlaid on images
  • Result storage and historical review

4. Configuration

Settings are split between .env (secrets) and config.yaml (everything else). The server reloads config.yaml on every request — no restart needed.

4.1 API Key (.env)

The Gemini API key is stored in .env (excluded from git via .gitignore):

GEMINI_API_KEY=AIzaSy...

4.2 Gemini Settings

gemini:
  default_model: "gemini-2.5-flash-lite"

4.3 Models

Each model entry defines id, name, group (for dropdown grouping), and input_limit (max input tokens for the usage bar).

models:
  - id: "gemini-2.5-flash-lite"
    name: "Gemini 2.5 Flash-Lite"
    group: "Gemini 2.5"
    input_limit: 1048576

4.4 Available Methods

The list of valid method_id values for the robot. Displayed as editable chips in the UI and injected into the prompt via {available_methods}.

available_methods:
  - ik_reach_object_v1
  - act_gripper_grasp_v1
  - act_gripper_release_v1
  - act_drawer_open_v1
  - act_drawer_close_v1
  - act_door_open_v1
  - act_door_close_v1

4.5 Prompt Template

Uses two placeholders replaced at runtime by the frontend:

  • {instruction} — the user's natural language instruction
  • {available_methods} — bullet list of methods

4.6 Verification

verify:
  enabled: true    # Enable/disable plan verification
  max_retries: 3   # Max infer+verify attempts

The verify_prompt_template uses three placeholders: {instruction}, {plan_json}, {available_methods}.

See Section 7: Verification Process for full details.

4.7 Storage

storage:
  results_dir: "data/results"   # JSON result files
  images_dir: "data/images"     # Uploaded images

6. Prompt Engineering

The prompt is designed around strict action sequencing rules for a single-arm robot.

6.1 Core Principle

Every act_* step MUST be preceded by ik_reach_object_v1. The robot must reach the target before interacting with it. This is enforced via:

  • Explicit action patterns in the prompt
  • A worked example showing the pattern
  • A closing recap reinforcing the rule

6.2 Action Patterns

TaskStep 1Step 2Example
Pick up objectik_reach_object_v1 → objectact_gripper_grasp_v1 → objectReach red cube → Grasp red cube
Place / releaseik_reach_object_v1 → destinationact_gripper_release_v1 → destinationReach green bowl → Release into bowl
Open drawerik_reach_object_v1 → draweract_drawer_open_v1 → drawerReach drawer handle → Open drawer
Close drawerik_reach_object_v1 → draweract_drawer_close_v1 → drawerReach drawer handle → Close drawer
Open/close doorik_reach_object_v1 → dooract_door_*_v1 → doorReach door → Open door

6.3 Container Logic

Container TypeBehaviorExample
CLOSED (drawer, door)Must open BEFORE picking up the objectOpen drawer → pick cube → place in drawer → close drawer (8 steps)
OPEN (bowl, tray, bin)Pick up object first, then reach container, then releasePick cube → reach bowl → release into bowl (4 steps)

6.4 Bounding Box Format

YOLO format: [x_center, y_center, width, height], all normalized to [0, 1]. If the model returns pixel values (any value > 1.0), the server auto-normalizes them using the image dimensions.

x_center = box_center_x / image_width
y_center = box_center_y / image_height
width    = box_width / image_width
height   = box_height / image_height

7. Verification Process

After generating a plan, the system sends the plan back to Gemini for verification. If verification fails, the entire inference is retried (up to max_retries times).

7.1 How It Works

  1. Infer — Call Gemini with image + prompt to generate a plan.
  2. Parse — Extract JSON from the response.
  3. Normalize — Auto-fix pixel bboxes to [0,1] if needed.
  4. Verify — Send the plan + image + instruction back to Gemini with a verification prompt.
  5. Retry — If verification fails, repeat from step 1 (up to max_retries times).

7.2 Configuration

verify:
  enabled: true    # Set to false to skip verification
  max_retries: 3   # Max number of infer+verify attempts

7.3 Verification Prompt

The verify_prompt_template in config.yaml uses three placeholders:

  • {instruction} — the user's instruction
  • {plan_json} — the generated plan as JSON
  • {available_methods} — bullet list of valid methods

The verifier checks: step ordering, action sequencing, bounding box accuracy, method validity, and completeness. It includes correct patterns for both OPEN and CLOSED containers to reduce false rejections.

7.4 Verify Result in API Response

"verify": {
  "enabled": true,
  "passed": true,
  "attempts": 1,
  "max_retries": 3,
  "history": [
    {
      "attempt": 1,
      "infer_elapsed": 2.31,
      "raw_response": "...",
      "verify_result": {
        "verified": true,
        "reason": "Plan correctly sequences all actions..."
      }
    }
  ]
}

If passed is false, the plan was not verified after all attempts. The history array shows each attempt's result and reason.

10. Frontend

Single-page app in static/index.html. The sidebar has one page: Step1-Planing(Gemini), which contains three inner tabs:

10.1 Planing

  • Token Usage: fetched from /api/token-usage on page load, updated after each inference
  • Model selector: populated from /api/config, grouped by model family
  • Instruction: text input, auto-injected into prompt template
  • Methods: chip-based, add/remove dynamically, auto-injected into prompt
  • Image: required, drag & drop or click to upload
  • Prompt: collapsible, auto-generated from template, editable for overrides
  • Result: canvas with bounding boxes + step cards + verify status + raw response

10.2 History

  • Grid of all historical results with bbox overlays on thumbnails
  • Filter by model
  • Shows verify status badge (passed/failed) and attempt count
  • Click to open detail modal (full steps, verification history, raw response, prompt)
  • Delete individual results

11. Running the Server

11.1 Install Dependencies

pip install -r requirements.txt

Dependencies: fastapi, uvicorn[standard], httpx, pyyaml, python-multipart, Pillow, python-dotenv

11.2 Configure API Key

Create a .env file in the project root:

GEMINI_API_KEY=your_api_key_here

11.3 Start Server

python main.py

Or with uvicorn directly:

uvicorn main:app --host 0.0.0.0 --port 8000 --reload

The server runs at http://localhost:8000

11.4 Configuration Changes

Edit config.yaml and refresh the browser. The server reloads the config on every API call — no restart needed.
